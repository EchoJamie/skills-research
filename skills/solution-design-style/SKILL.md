# 方案设计风格

用于把复杂需求转化为可实施的方案思路。目标是控制复杂性，而不是堆砌组件、流程图或“最佳实践”。本技能不替代项目已有规范、当前代码调查或用户已确认的业务决定。

## 设计取向

- 先明确边界和不变量，再选择模块、接口、表或框架。边界包括业务与数据所有权、权威身份/租户来源、外部系统责任和不得改变的既有行为；不变量包括隔离、唯一性、一致性、恢复和敏感数据边界。
- 优先显式模型。身份、权限、配置来源、状态、失败原因和输入版本应可追踪；不要依赖角色字符串、调用顺序、默认回退或隐式上下文来承担关键语义。
- 优先确定性。遇到歧义匹配、冲突、异常外部数据或权限不足时，设计可解释的拒绝、保守降级或人工处理路径；不以猜测式自动化换取表面成功率。
- 优先演进式集成。新能力只替换真正变化的责任段，复用既有成熟链路；避免复制认证、权限、会话、租户或数据管理体系。若必须改变公共链路，明确扩大范围和回归影响。
- 将长时、异步或可重试过程建模为生命周期，而非一次请求。定义输入何时冻结、状态如何迁移、并发如何仲裁、失败如何恢复、终态如何清理和结果如何查询。
- 将外部系统隔离在窄适配层内。外部路径、字段命名、错误、认证和超时由 Client/Adapter 消化，内部领域不直接继承外部实体或隐式规则。
- 技术机制必须服务于一个已说明的业务约束。索引、锁、事务、租约、DTO、迁移、缓存和前端状态都要能回答“保护什么”；不要因技术显得高级而引入。

## 使用方式

1. 先区分：用户已决定的目标、当前可核验事实、仍待选择的设计，以及尚未验证的假设。不要把历史方案或已有代码直接当作需求权威。
2. 先写出影响方案的边界和不变量，再提出候选方案。对每项重要选择说明它保护的约束、承担的组件，以及不采用的替代路径及理由。
3. 为状态变化、外部调用、并发写入和跨租户访问补足失败路径。特别检查重复请求、配置漂移、部分完成、竞态、数据缺失、权限变更和重试。
4. 仅在事实支持时复用现有能力；复用时说明保持不变的行为。发现现有链路与方案前提冲突时，停止静默套用并把冲突列为待决项。
5. 输出应优先呈现决策与理由，而不是固定套用章节。通常应让读者看清：边界、关键不变量、核心模型/数据流、异常与并发处理、集成方式、演进和验证边界。

## 约束

- 不把这里的原则变成脱离需求的强制模板；简单、同步、局部的能力不必虚构状态机、适配层或独立服务。
- 不用“安全”“兼容”“可扩展”等泛词替代可验证设计。安全与运维机制应与已确认的数据分类、威胁和运行条件匹配。
- 不把静态审查、单测或构建通过表述为真实 HTTP、数据库、浏览器、部署或回滚验收。
- 保留用户的明确产品选择；当多种方案都合理时，展示关键取舍，不擅自把偏好升级成需求。
