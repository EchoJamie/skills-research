# 方案细化

## 目标

以上一阶段确认的整体步骤和用户决策为主干，自主补齐真正必要的设计细节，使方案完整、连贯且可进入后续拆分设计。目标是补足缺口，不是追求篇幅或罗列所有可能性。

## 开始前检查

1. 读取当前工作区规则、待细化方案和相关代码事实，区分已确认决策、主流程、事实与未验证假设。
2. 确认当前对象只有一个连贯目标。若仍包含多个可独立达成的结果、多条独立主线或大量互不相关的关键决策，停止细化并建议先做目标或阶段拆分，不能直接生成臃肿方案。

## 细化方式

1. 沿已确认的整体步骤逐项检查，找出会导致流程断裂、行为不明确、边界不清或无法判断结果的设计缺口。
2. 对每个候选细节先询问自己：它与哪个决策或主流程步骤相关？如果不补会发生什么？它是否真的需要进入本阶段方案？
3. 必要且能由当前事实唯一确定的细节由智能体自行补齐；不会影响方案成立的内容不加入；局部实现偏好留给后续设计或开发。
4. 必要但存在多个会改变目标结果、整体路径或重要边界的方向时，将其升级为关键决策，等待用户选择后再继续定稿。
5. 把新增细节和用户决策融入受影响的步骤，持续检查前置条件、衔接和完成结果，不能只在文末追加说明。
6. 将用户要求转化为可由执行 agent 自行验证的验收目标，至少明确可观察结果、通过标准和应保留的证据类型；除非方案、契约或项目规则已经固定，不在本阶段规定具体命令和工具。
7. 所有必要设计已经闭合、验收目标可执行且关键决策均已关闭后，向用户发起本阶段最终确认。确认消息必须明确说明：用户确认后将直接使用 `$solution-to-development-toolkit` 生成开发工具包，不再询问是否进入下一阶段。发出确认问题后，本技能处于等待确认状态，尚未完成。
8. 用户确认后，不只回复“已确认”、复述结论或结束回合。从可用技能列表定位并完整读取 `$solution-to-development-toolkit` 的 `SKILL.md`，在当前回复中立即按其开始条件继续执行。只有下一技能识别出新的关键决策、新增授权要求或外部阻塞时才暂停；完成交接后，本技能才算完成。

## 相邻技能

- 上一阶段是 `solution-step-alignment`。若整体步骤、目标边界或关键决策尚未锚定，返回上一技能处理，不在本技能中越过缺口继续丰满。
- 下一阶段是 `solution-to-development-toolkit`。使用它开始生成开发工具包是本技能的必需完成动作，不是提供给用户选择的后续建议；两个阶段之间不发送只表示当前阶段完成的独立回复。
- 未得到最终确认时停留在本阶段；不能以自动衔接为由跳过关键决策、替用户确认或提前读取下一技能。

## 关键决策

- 不代替用户作出关键决策，也不把智能体推荐默认为已确认方向。
- 提问时至少给出两个真实可行方向，说明各自对主流程、范围或目标结果的主要影响，并允许用户补充新方向。
- 用户未决定时标为待决策，不沿某个方向继续定稿。事实只剩一个可行方向时，将其作为约束说明，不虚构选项。

## 安全细节

- 安全性不能单独成为扩展理由。先说明需要保护的对象、相关数据或信任边界，以及不处理时的具体后果。
- 与已确认目标和主流程没有直接关系，或只是泛化的最佳实践时，不加入本期方案。
- 必要的安全目标若能由现有约束唯一确定，由智能体补齐；若多种措施会明显改变体验、兼容、成本或主流程，则按关键决策交给用户。

## 方案文档

继续更新对应的 `<功能主题>方案.md`，保持整体步骤为主干，按实际需要补充边界、职责、交互、数据、异常和可由 agent 执行的验收目标，不强制保留空章节。

## 边界

- 不改变上一阶段已经确认的目标和决策；发现冲突时停止静默细化并交给用户处理。
- 本技能不拆分开发任务、不制作开发工具包，也不修改业务代码；用户确认后的开发工具包工作由交接后读取的技能负责。
- 不用穷举异常、安全、兼容或扩展性细节来制造表面完整。
