## 2. 运行过程

1. Skill 被显式加载，主智能体创建并复用了用户可见的 Herdr Agent。
2. 三个边界独立的责任同时派发后，Agent 能够并行形成结果，证明 Herdr 工作面本身能够提供并发执行能力。
3. 进入大规模整改窗口后，主智能体连续承担多项实现和整合工作；同一窗口没有新的 Herdr prompt，已有 Agent 完成短责任后进入 `idle` 或 `done`。
4. Herdr 不会把邻居 Agent 的完成事件主动注入主会话。主智能体没有在开始后继工作前形成回填检查点，结果是自己继续吸收可委派工作。
5. 后段增加状态读取、等待和短责任续派，只形成过突发并行，没有改变 Agent 完成后长期空闲的模式。
6. Herdr 仍有可用负责人时，主智能体又启动或续派了不可见内置子代理，偏离了显式调用后的可见协作约束。
7. 用户需要再次提醒主智能体继续使用该 Skill，说明第一版没有把持续遵循与退出条件写成首要约束。

## 3. 第一版暴露的问题

| 问题 | 运行证据 | 第一版原因 |
|---|---|---|
| 主智能体成为唯一关键路径 | 大规模整改窗口有大量主线工作，但没有对应 Herdr prompt | “全局影响工作”范围过宽，把契约冻结后的跨模块实现和局部验证也留给了主智能体 |
| Agent 完成后长期饥饿 | 短责任结束后负责人进入 `idle/done`，后继工作仍由主智能体完成 | 第一版只要求完整责任，没有规定开始新工作前优先回填已就绪责任 |
| 可见协作发生机制漂移 | Herdr 有空闲容量时仍使用不可见内置子代理 | “默认使用 Herdr”没有覆盖 Skill 生效后的所有新并行责任 |
| Skill 在执行过程中被遗忘 | 用户需要反复提醒继续使用 | 没有明确触发后的持续遵循和唯一退出条件 |
| 责任链长度不足 | 单次审计或单文件任务很快完成 | “完整局部责任”仍容易被解释成一个短工作包，没有包含同一所有权内的实施、修复和验证 |

## 4. 阶段结论

第一版解决了“主智能体不能退化成纯等待者”，但没有解决相反方向的问题：主智能体可能借“持续执行”和“全局工作”吸收多数关键路径，使 Herdr Agent 只在短时派发后等待。

第二版整改需要同时满足：

- 主智能体保留目标级决策、冲突裁决、集成时机和最终结论；
- 已冻结契约下的独立实现和局部验证可以形成 Herdr 责任链；
- 主智能体开始新工作前检查并优先回填可用负责人；
- 工作包覆盖同一所有权内能够连续推进的相邻工作；
- Skill 生效后的新并行责任保持在 Herdr 可见工作面；
- 显式调用后持续遵循，只有用户明确要求时退出。
