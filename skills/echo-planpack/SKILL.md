# 功能实施规划

## 定位

把已经确定的功能需求转换为可审核、可确认、可交接的实施规划。先形成并稳定方案，再生成不包含实际代码的开发工具包，最后生成人类可读的目标与边界总结。

只负责规划产物，不修改业务代码，不生成补丁、正式迁移文件、配置改动或其他实际实现产物，也不替代独立审核者。

## 开始前判断

1. 确认需求功能和关键产品决策已经确定，当前目标是形成具体实施计划。
2. 若仍在澄清需求、比较产品方向或决定是否建设，停止本技能并先完成需求定义。
3. 若任务只是简单局部修改、只读诊断、代码审查或直接开发，说明本技能不适用，不扩大流程。
4. 读取当前工作区及目标仓库的 `AGENTS.md`、规则文件和写入边界。尊重只读目录、用户现有改动和权限限制。
5. 确定一个专属的功能规划目录。用户未指定时，只能在项目规则允许的文档区域提出或创建，不得把产物写入只读源码目录。
6. 读取 [references/workflow.md](references/workflow.md) 后再开始规划。

## 必须遵守的边界

- 使用自然语言的“阶段”“任务”“确认事项”等名称，不使用 `G`、`WP` 或容易与优先级混淆的 `P1/P2` 表示流程结构。
- 不为展示并行关系而设置并行组。任务以事实性前置依赖为准；当需求、交付组织或真实依赖要求多条可独立推进的工作流时，可以明确写出独立交付流、共享契约和汇合门槛，但不能为了追求并行而拆分。
- 不强制使用阶段/任务二级目录；按实际复杂度组织，避免过度拆分。
- 《实施方案与计划》保留所有实质版本；开发工具包只保留当前有效副本，不保留历史版本。
- 审核记录必须位于开发工具包之外。开发工具包应能脱离方案与审核记录独立分享和执行。
- 工具包不得包含规划机器的绝对路径。代码定位使用仓库内相对路径、模块名、符号名和必要的定位提示。
- 行号只作为定位提示，不构成修改授权。
- 用户仍只对独立审核通过后的具体方案执行正式基线确认。若尚有会改变模块归属、跨系统契约、交付流、兼容策略、用户交互或发布路径的高影响决策，必须在完整方案形成前进行一次轻量决策对齐；这不是正式方案确认，也不默认生成文件。工具包完成后不再设置常规用户确认断点。

## 执行工作流

### 1. 建立送审基线

读取已经确定的需求、已有决策和当前代码。把输入区分为规范性来源、兼容约束、事实性来源和历史参考；历史文档或旧方案不得整份自动提升为当前规范。引用兼容约束时必须限定具体适用章节、规则或行为，不能用笼统的“整体适用”扩大本期义务。

在写方案前封闭送审范围：

- 列出直接受影响的行为链和模块；
- 枚举每项“保持不变”行为的具体对象、当前事实、影响关系和验收方式，不使用开放式的“所有既有行为保持不变”；
- 列出范围外内容和审核者允许扩展范围的条件；只有能举证其与本期变更存在直接依赖时，范围外路径才能成为本期阻断；
- 为关键事实分配稳定编号，记录仓库相对路径、符号、核验方式、核验日期、内容摘要或其他可判定指纹、未验证范围和所支撑的设计/验收。

送审范围和事实证据索引默认写入方案相应章节及审核交接，不强制增加正式文件。内容很大时，可在项目规则允许的位置创建当前过程资料，但必须位于开发工具包之外，也不能成为工具包执行时的外部依赖。

只进行规划所需的只读检查。未得到用户授权时，不运行会改变代码、Git、数据库、部署或外部系统状态的操作，也不以构建或测试代替事实调查。

### 2. 对齐高影响实施决策

在生成完整方案前，判断现有需求、项目规则、用户决策和工程事实是否已经唯一确定下列高影响事项：

- 主要能力的模块、服务或仓库归属；
- 跨系统接口、数据或安全契约；
- 单线实施还是多条独立交付流，以及它们的共享契约和汇合门槛；
- 兼容、迁移、发布和回滚策略；
- 用户可见功能的主任务流、信息层次和关键交互结构；
- 会实质改变范围、任务所有权或验收证据的其他取舍。

已经由规范性来源或可核验事实唯一确定的事项直接继承，不重复询问。仍有多个合理选项且选择会导致方案主体或任务拆分重写时，在对话中给出一份简短的“实施决策摘要”：每项写明当前事实、2～3 个可行选项、推荐项和主要代价，只请求真正需要权威选择的 1～3 项。等待用户决定后再生成完整方案。

不要把实现者可在既定边界内自行决定的局部结构、命名或代码组织提升为用户决策。用户未要求留档时，实施决策摘要只保留在对话中；用户决定应作为当前方案的规范性来源记录。

### 3. 生成或修订实施方案

读取 [references/implementation-plan-template.md](references/implementation-plan-template.md)，生成 `实施方案与计划_v<版本>.md`。若功能目录中已经存在未确认的方案草案，先判断能否承接：在目标、范围和关键决策仍有效时，以当前事实补齐并规范化为候选版本，不从零重复生成；已经送审的版本仍不得原地修改。

- 第一个候选版本通常为 `v1.0`。
- 任何影响目标、范围、契约、依赖、验收或实施路径的实质修改都生成新版本，旧版本保持不变。
- 仅排版或错别字修正是否升版，要根据其是否改变送审摘要和审核可追溯性谨慎判断；已送审或已确认文件不要原地修改。
- 方案必须覆盖需求、现状证据、范围、约束、关键设计、实施顺序、验收、风险和未决阻断，但不机械保留不适用的空章节。

完成后按模板末尾的自检和送审准备清单检查。存在开放式保持不变声明、未封闭的生产读写/消费入口、未限定的历史规范来源、验收孤儿或不可判定门槛时，继续规划，不要把明显未准备好的版本送入昂贵的独立审核。

规划者可以把自检发现和已知风险作为“待独立核验线索”交给审核者，减少重复搜索，但不能把预期结论、通过压力或指定修复方案当成审核输入。审核者必须独立判断线索是否成立、是否阻断。事实证据索引和送审范围仍只是导航和可核验输入，不自动构成证明。

### 4. 显式委托方案独立审核

定位并显式调用 `$echo-planpack-review`。首次方案审核使用不继承本会话完整历史的新子代理，并只提供最小充分上下文。保存该审核会话或子代理的可继续委托标识；同一方案的后续复审必须优先复用首次审核者，不要每轮新建审核者。技能源码并列存放时，可让审核者读取相邻的 `../echo-planpack-review/SKILL.md`。

只有用户明确要求使用 Herdr 时，才按 `$herdr` 技能创建和协调独立审核代理；否则直接使用当前环境提供的合格独立审核机制，不增加工具可用性探测或额外编排层。

委托前读取 [references/review-handoff-template.md](references/review-handoff-template.md)。审核者必须有权：

- 读取被审核方案及限定来源；
- 在 `方案审核记录/` 新建一份审核记录；
- 计算开始和结束摘要；
- 返回审核结论与记录路径。

只会继承规划会话完整历史的子代理不满足独立性要求，其结果只能作为辅助复核。没有合格子代理、创建失败、超时或没有生成有效记录时，直接在对话中输出一段可复制到新会话的审核交接提示词并停止在“待独立审核”，不得以自检代替审核。除非用户明确要求留档，否则不要把该提示词写入功能规划目录或作为正式产物。

审核不通过时，根据审核记录生成新的方案版本，再重新自检和独立审核。复审输入包括当前方案、上一轮审核记录、实际用户修改意见、版本变化说明、受影响事实编号、待独立核验线索和是否命中全量事实复查条件。

复审时向原审核会话追加任务。只有原审核者不可继续、独立性受损、上下文已经丢失，或本轮改变规范来源、目标范围或主要模块边界而需要重新建立独立基线时，才创建新的审核者。重新创建时必须在交接中说明原因。

### 5. 请求并记录用户确认方案基线

只有审核结论为“通过：没有未解决阻断问题”时，才能请求用户确认。明确给出：

- 方案相对路径和版本；
- 文件 SHA-256 摘要；
- 本次确认覆盖的目标、范围、关键约束和验收；
- 尚保留的非阻断风险或确认事项。

只有用户明确确认后，才在 `方案审核记录/` 新建 `YYYYMMDD-NN-用户确认方案基线.md`，记录确认时间、方案路径、版本、摘要、确认范围、保留事项和用户原始确认表达。不得把模糊回复或无回复解释为确认，也不得为写入“已确认”而修改已确认的方案正文。

### 6. 生成当前开发工具包

确认方案基线后，读取 [references/development-toolkit-template.md](references/development-toolkit-template.md)，生成或重建 `开发工具包/`。

开发工具包只能包含计划和任务规格，不得包含实际实现代码。它必须：

- 记录来源方案版本和摘要，但不要求执行者取得方案文件；
- 在自身 `README.md` 中完整说明总目标、范围、共同约束、任务索引、事实性依赖和整体验收；
- 使每个任务单具备目标、边界、规划时现状、前置出口事实、开工复核、实施要求、验收证据、停止条件和执行结果格式；
- 用需求到任务、任务到验收的映射检查遗漏；
- 只按实际工作边界拆分任务，不为追求数量或并行度过度拆分。

若任务所有权、跨仓库独立交付流或汇合门槛尚未在已确认方案中确定，不得由工具包自行发明；停止并回流方案。已确认方案明确存在独立交付流时，工具包应按共享契约和真实依赖表达，使各执行者无需等待无关实现完成。

在每一轮审核开始前完成自检并冻结工具包。使用 `scripts/artifact_digest.py 开发工具包/` 计算整体摘要。

### 7. 显式委托开发工具包独立审核

再次显式调用 `$echo-planpack-review`，审核类型设为“开发工具包审核”。默认复用方案首次审核者：该审核者仍独立于规划者，并且已经建立过方案事实基线，可以专注检查“已确认方案是否被正确转换为任务”。只有审核者不可继续、独立性受损、上下文丢失，用户明确要求新审核者，或工具包引入方案未覆盖的高风险事实且需要重新建立独立基线时，才创建新的审核者并记录原因。

把已确认方案作为唯一的方案规范来源。工具包审核默认检查需求/设计到任务、依赖、权限和验收的转换，不重新设计方案，也不从代码现状创造新要求。代码和项目文件只在工具包新增事实断言、相关指纹变化或命中高风险事实复查条件时核验；不得仅因切换到工具包对象就从零重查全部代码。

- 属于工具包的问题：在本轮审核结束后修改或重新生成当前工具包，不保留旧副本，再重新自检、计算摘要和复审。
- 属于已确认方案的问题：只报告，不修改方案；停止流程，等待用户决定是否重新打开方案。
- 属于事实阻塞：报告缺失的事实或权限及其影响，停止猜测。
- 非阻断风险：必须落实到对应任务的约束、停止条件或验收要求后，才能保留“通过”结论。

同一开发工具包的后续复审继续复用当前审核者，并按“完整检查当前工具包一致性、重点复核改动和受影响依赖”的方式进行。复审记录可以引用上一轮稳定来源和事实，只记录变化、旧问题闭环、新发现和结论，不重复抄录不变的完整事实表。

同一根因经过两次方案或工具包修订仍是阻断问题，或出现规范来源分歧、已解决问题复现、对象持续不稳定、缺少权威事实/权限、只能降低验收或缩小既定范围才能通过时，触发熔断并向用户报告，不得继续自动改写。

### 8. 生成最终总结并结束

只有开发工具包审核通过且送审对象摘要一致时，读取 [references/target-boundary-template.md](references/target-boundary-template.md)，生成 `目标与实施边界.md`。

对已确认方案、当前工具包和最终总结执行一致性检查，确认目标、范围、约束、任务覆盖和验收没有漂移。然后结束规划流程，不开始开发。

最终向用户报告产物位置、确认的方案版本与摘要、最后审核结论、工具包摘要、剩余非阻断风险，以及如何在新会话中直接提供 `开发工具包/` 路径开始执行。

## 资源使用

- 始终读取 [references/workflow.md](references/workflow.md) 获取状态转换、文件生命周期和异常出口。
- 写方案时读取 [references/implementation-plan-template.md](references/implementation-plan-template.md)。
- 方案确认后写工具包时读取 [references/development-toolkit-template.md](references/development-toolkit-template.md)。
- 委托审核或跨会话交接时读取 [references/review-handoff-template.md](references/review-handoff-template.md)。
- 最终生成总结时读取 [references/target-boundary-template.md](references/target-boundary-template.md)。
- 使用 `scripts/artifact_digest.py` 计算单文件或目录的稳定摘要，不手工拼接目录摘要。
