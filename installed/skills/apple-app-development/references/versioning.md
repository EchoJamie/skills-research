# 按发布批次管理版本

产品版本标识一次发布所包含的一批变更。提交、PR、需求和缺陷用于组织开发工作，与版本号递增没有一一对应关系。沿用项目现有版本事实源、构建号机制和变更记录位置。

## 1. 确认是否进入新版本准备

日常开发、修复、提交、合并和普通打包均不自动修改产品版本，即使本次包含新功能。Release 构建配置只决定构建方式，不等于发布新产品版本。

用户明确要求准备新版本、指定版本号，或当前已确认的发布计划进入版本准备阶段时，再执行后续步骤。不因智能体把某个任务分类为功能或缺陷，就立即发动升版。

## 2. 汇总本次发布范围

以上一次正式发布为基线，汇总本次计划发布的全部功能、修复和优化，而不是只看最后一个提交。复用现有变更记录、PR 或提交历史；项目已有未发布记录时继续维护，没有时在版本准备阶段统一整理，不另建逐提交升版或记账机制。

一个次版本可以包含多个需求和缺陷修复，一个补丁版本也可以集中包含多个缺陷修复和优化。

## 3. 为整个批次确定一次版本

| 本次发布包含的变化 | 相对上次正式发布的产品版本处理 |
|---|---|
| 仅修复缺陷或优化现有功能 | 递增一次 `z` |
| 包含新增功能或产品特性，也可同时包含修复 | 递增一次 `y`，将 `z` 归零 |
| 主版本变更 | 只有开发者明确决定时才调整 `x`；确定后低位归零 |
| 没有新变更，仅重建已有版本 | 不自动递增产品版本 |

产品版本使用 `x.y.z`。识别到不兼容变更时说明影响，由开发者决定主版本，不自行递增 `x`；`0.y.z` 不因分发而强制变为 `1.0.0`。

已经确定但尚未发布的目标版本可以继续聚合本批次变更，不随新增提交重复递增。例如上次发布为 `1.4.2`，本轮三个功能和五个修复一起发布为 `1.5.0`；准备期间再加入修复仍是 `1.5.0`。若原计划为补丁版本但发布范围后来加入新功能，以上次正式发布为基线重新确定一次目标版本，不把每次范围变化累加为版本增量。

用户已指定版本时沿用；若它与已确认的发布范围或已发布版本冲突，说明具体冲突后再确定，不擅自替换。

## 4. 同步应用元数据与发布记录

确定本批次目标版本后，更新现有版本事实源，使构建结果的 `CFBundleShortVersionString` 与之相同。`CFBundleVersion` 独立作为构建号，新的交付版本保持单调递增，同版本重建沿用项目已有机制；它不代替产品版本，也不要求二者相等。

为整个发布批次整理一份 changelog 记录，包含版本号、发布日期和用户可见变化；准备期间可以补充同一份未发布记录。使用 `Added`、`Changed`、`Fixed`、`Performance`、`Security` 中适用的分类，不保留空分类。新建 changelog 默认按发布时间正序追加，已有项目保留其明确排列约定。

正式发布后，该版本及其记录固定，不修改、删除或重新排序，也不把后续新变更补到已发布版本中。后续变更积累到下一批发布；普通本地试用包仍可按项目规则重建，但不覆盖已发布 Release 的内容。

## 5. 在创建和推送 tag 前完成发布准备

在现有发布准备入口校验产品版本格式、项目要求的构建号格式、App 元数据与本次 changelog 版本，以及目标提交和发布分支约定；没有脚本时按这些内容完成发布前核对，不另外搭建通用检查框架。此时尚未创建或推送 tag，任一不满足就停止发布准备。版本在签名前写入，包名读取同一来源；构建流程见 [build-and-package.md](build-and-package.md)。

使用 `vX.Y.Z` 标签发布时，先确认拟用标签与本批次版本、目标提交一致。使用本 Skill 的产品 workflow 模板时，将本次 changelog 内容及签名／公证说明准备为附注 tag 的正文；已获相应授权后才创建并推送该 tag。使用 Markdown 正文创建附注 tag 时，传入 `git tag -a --cleanup=verbatim -F <临时正文文件> <tag> <目标提交>`，保留以 `#` 开头的标题；临时正文文件用完清理。GitHub Actions 消费已准备好的 tag、源码和发布说明，不重新校验版本关系，也不推算或递增版本。

准备版本和生成 DMG 不隐含提交、推送、创建远端标签或发布授权。已获发布授权时，由 [GitHub Actions 工作流](github-actions.md) 或项目现有发布入口执行。
