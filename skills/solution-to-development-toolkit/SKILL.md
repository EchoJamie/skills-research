# 方案转开发工具包

## 目标

在已确认功能、质量和资源条件下，以缩短从规划到整体目标验收的时间为取向，将必要工作组织为可执行的任务包。拆分需兼顾总工作量、串行依赖、实际并行条件与交接返工成本；任务包是明确结果、边界、依赖和验收的委托契约。

本技能只生成和修订文档，不修改业务代码，不执行任务，也不替用户改变已确认方案。

## 开始条件

1. 读取工作区规则、已确认方案和支撑方案的当前代码事实，区分用户决策、事实、假设与待确认事项。
2. 确认方案目标、边界和关键决策已经关闭。若仍需丰满方案，返回方案细化；若仍包含多个独立目标或多条主线，先返回目标或阶段拆分。
3. 按项目规则确定一个专属的 `<功能主题>开发工具包/` 目录。
4. 确认 `toolkit_architect` 可用；方案涉及前端、客户端或其他用户终端时，还必须确认 `interaction_designer` 可用。缺少必需角色时停止并报告，不能用普通代理静默替代。
5. 读取 [references/task-package-template.md](references/task-package-template.md)。

## 相邻技能

- 上一阶段是 `solution-refinement`。若方案的目标、整体步骤、必要设计、验收目标或关键决策尚未关闭，返回上一技能继续细化；若问题来自目标过大，再由上一技能衔接 `solution-step-alignment`。
- 当前方案系列尚未定义本技能之后的技能。开发工具包完成一致性检查后停在本阶段边界，不自动领取或执行任务包。

## 角色与文档所有权

- `toolkit_architect` 对专业拆分结论负责，写入开发工具包 `README.md`、执行结构、依赖关系和全部任务包文件。
- `interaction_designer` 对必要交互及其落实负责，写入 `交互设计.md`，只读检查终端任务包。
- 主对话提供共同基线、核对事实与交付一致性、组织分歧处理和最终交付。专业代理结束写入后，可以整理交付文档；涉及拆分或交互结论的实质修改交对应角色修订或核对，不以最终整合权代替专业判断。
- 两个专业代理只允许写主对话明确分配的文档路径，不修改业务代码、Git 状态或其他文件。

## 专业代理创建方式

- 使用可用的 `toolkit_architect` 和 `interaction_designer` 专业角色创建子代理会话，不以普通代理模拟专业角色。
- 创建消息明确本轮角色身份，提供最小充分交接、具体任务、输入文档、本次使用的 Skill 与模板路径、输出路径和期望出口。角色的稳定职责由对应 Agent 配置定义，创建消息不重复整份角色说明；后续修订优先继续委托同一角色会话。

## 协作流程

### 1. 建立共同基线

主对话整理已确认方案、决策、相关事实、项目规则和输出安排。提供已知的执行者、可用并行能力及共享写入限制；未知条件标为假设，不按无限资源规划。专业角色针对职责核验相关当前实现，不重复无关调查，也不将另一个角色的意见当作既定事实。

### 2. 形成执行结构与必要交互

在职责互不冲突时，同时委托：

- `toolkit_architect`：先识别必要改动及真实依赖，再依照下方拆分判据组织任务，将执行结构、主要取舍和未决边界写入 `README.md`。
- `interaction_designer`：复用已确认的交互设计，补足任务落实所需的流程、状态和验收，写入 `交互设计.md`；优先指出影响拆分的入口、共享状态与场景边界。

影响拆分或终端行为的必要结论尚未稳定时，不要求架构师预写完整任务包正文。输入已充分稳定时可直接成稿，不机械增加一轮确认。等待必需专业结果后定稿；主对话可先核对已返回内容，不为填满等待时间增加产物。

### 3. 主对话分析整合

主对话读取实际文档与角色结论，依据已确认方案和事实定位遗漏、矛盾及其影响，向对应角色提出具体修订要求。

- 先判断分歧属于事实错误、职责越界、设计缺口还是用户关键决策。
- 事实错误直接指出依据；拆分与依赖问题由架构师收束，交互问题由交互设计师收束。跨专业矛盾由主对话组织两者核对相关依据，不自行补成新设计。
- 只有事项会改变已确认的目标结果、整体达成路径、关键用户流程或方案实质边界时，才升级为关键决策，说明事实、可行方向及影响并等待用户决定。
- 后续委托必须包含主对话自己的判断、待解决问题和期望出口，不使用“另一个代理说……”代替分析。

### 4. 收敛任务包

关键事项关闭后，由架构师完成任务包正文；已有可用正文只补足缺口。交互设计师只读检查终端相关内容，架构师据具体问题修订。结论变化时核对受影响的任务包与依赖；影响范围无法确定时再扩大检查，不默认整套重写。

架构师将以下内容纳入终端任务包，交互设计师核对其是否正确落实：

- `交互设计依据`的相对路径和具体章节；
- 本任务包实际需要落实的用户流程与交互状态；
- 对应的交互验收要求；
- 与其他终端场景的边界。

不能只放一个笼统的交互设计文档链接。交互设计变化后，重新检查所有引用受影响章节的任务包。

### 5. 完成一致性检查

完成前，架构师核对执行结构是否满足拆分判据，交互设计师核对终端任务包。主对话汇总专业结论并检查：

- 方案中的每项实质目标和约束都有任务包或工具包级落实位置；
- 各包结果、前置、写入边界与整体功能验收责任一致，专业分歧和关键决策已经关闭；
- 任务包按模板保留必要信息、删除不适用内容，并引用共用执行与证据口径；
- 工具包没有包含业务代码、补丁或未经确认的新方案设计。

检查通过后结束，不开始开发。文档检查不能证明真实执行已提速，效率收益需结合实际执行中的等待、交接和返工验证。

## 任务包拆分判据

- 先识别完成目标所需的改动及真实依赖，再组织任务包。对影响执行结构的重要边界，比较合并与拆分对总工作量、最长依赖链、实际并行条件和交接返工的影响；没有可靠耗时依据时说明取舍，不编造工期，也不逐包生成论证报告。
- 每个包及其新增职责、接口、状态、适配都应服务于已确认目标。当前实现边界或已确认的必要新边界须能支撑可交付结果；不为分工预造可接线组件或重复机制。文件所有权分开、前置清楚和局部可测不能单独证明拆分合理；一个任务包也可以构成完整工具包。
- 每包负责明确的必要改动和本包验证，不要求各包独立实现完整用户功能。跨包功能须明确真实入口、关键行为的归属，以及由谁负责组成完整功能并完成整体验收。局部完成不等于功能完成；名为“整合”的包若包含实质功能，按实际结果明确责任，不能只写接线并承接未分配工作。
- 创建者明确结果、边界、既定机制、硬前置和验收；领取者自主选择既定机制内的局部实现、具体文件、包内步骤和必要检查，并自行完成验证。自主权不包括另设跨模块或跨包职责、接口、共享状态、生命周期及恢复机制；未闭合的机制交主对话协调相关专业角色处理，不能以“本包需要”为由新增。
- 不按场景、文件、类、接口或技术层的数量机械拆分。相关工作共享入口或状态且没有自然边界时，优先同包；确有独立实现区域时，可以共同服务于一个用户目标。
- 前置条件指向开工所需、可观察的结果，不只写任务编号。具备并行条件还需共享机制一致、写入范围无冲突且执行资源允许；共享写入须明确归属或必要串行协调。编号只用于识别，不预设人为并行组或全局顺序。

## 开发工具包

- `<功能主题>开发工具包/README.md`：工具包索引与共用约定。
- `<功能主题>开发工具包/交互设计.md`：仅涉及用户终端时生成。
- `<功能主题>开发工具包/任务包/<任务包标识>-<名称>.md`：任务包。

`README.md` 保存来源方案、目标与范围、执行结构及主要取舍、资源假设、共同决策与约束、任务包索引、真实依赖、可领取条件和总体验收责任。共用评审应同时检查功能结果与新增内容的必要性。共享契约仅在目标本身需要且多个包共同依赖时单独成文；优先引用既有来源，不预建占位文件或额外检查报告。

共用执行与证据口径放在 `README.md`：领取 agent 自行执行指定检查及覆盖实际改动的必要检查，失败时在责任范围内修复并重跑；必需外部条件不成立时报告影响与缺口。未执行或未通过的必需验收不能记为完成；能自动执行的检查不设人工卡点，只有关键决策或新增授权交还用户。

每包只保留理解并开展本包工作所需的相关决策、非显然事实、边界、既定机制、前置和验收，使领取者无需重读完整方案。除方案或契约已固定的要求外，不指定详细实施步骤；通用规则引用 `README.md`。项目特有字段按项目规则或用户要求填写。

## 边界

- 不新增默认测试、安全、审核或其他专业角色；真实使用证明存在持续缺口后再决定是否增加。
- 不运行构建、测试、部署、Git 写操作或外部系统变更来代替文档规划。
