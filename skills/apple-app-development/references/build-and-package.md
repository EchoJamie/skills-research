# macOS 构建、签名与 DMG 交付

签名是构建打包链路中的一个阶段。由项目同一个入口完成构建、组装、签名、封装与清理；本地和 GitHub Actions 复用该入口。调整产品版本或准备新版本交付时读取 [versioning.md](versioning.md)；接入 Actions 时再读取 [github-actions.md](github-actions.md)。

## 模板接入

新建或统一普通 macOS App 的打包入口时，复制 [assets/build-dmg.sh](../assets/build-dmg.sh) 到项目的 `scripts/build-dmg.sh`。模板使用系统 Bash 3.2，固定构建 Release；本地和 CI 都运行 `bash scripts/build-dmg.sh`。已有脚本完整覆盖相同流程时继续复用，不额外包一层模板。

项目只适配以下位置：

| 位置 | 项目填写内容 |
|---|---|
| 顶部参数 | 产品名、可执行产品名、Info.plist 位置、输出目录；`SIGNING_IDENTITY` 使用项目固定的 Apple Development 身份，通过现有配置或环境传入 |
| `build_app` | 实际 Release 构建命令，将完整 App 写入 `APP_PATH`；模板提供可运行的 SwiftPM 组装方式，Xcode 项目替换为构建并复制 App，资源在此补齐 |
| `sign_app` | 无嵌套组件时直接沿用；有动态库、helper 等时先逐项签名，再签主 App，保留各自的 entitlements 和签名参数 |
| `DMG_PATH` | 新项目使用产品名、实际版本和架构；已有项目仅在此保留其固定命名 |

版本从组装后的 App 读取，不另维护一份；架构从实际二进制读取。产物组装、签名、封装和清理保持模板的共同顺序。同一输出路径串行打包。

模板面向拖放式 App，默认包含 Applications 入口；输入法、扩展和专用安装器沿用自身载荷布局，不能直接套用该布局。模板不会安装、启动应用、提交或发布，也不生成 manifest、检查报告或日志副本。编译缓存保留，临时 App 与镜像暂存用完清理。日常打包不挂载镜像，也不创建配套挂载状态。

## 确认本次构建

- 先找到项目已有的构建、签名、打包入口及其调用关系。确认打包命令会重新构建，还是仅封装传入的 App；后者需要先确认该 App 包含本次目标修改，不能仅凭路径存在就交付。
- 用户打包默认 Release，但构建配置不代表新产品版本发布，普通打包不自动升版。若底层构建脚本默认 Debug，由交付入口显式选择 Release；不要把整个开发工具链都改成 Release，也不要只改产物名称来伪装配置。
- 复用现有入口，让本地与 CI 调用同一构建／打包逻辑。缺少入口时按上节模板适配，不另造一套跨项目打包框架或把完整脚本复制进 workflow。
- 沿用项目明确的干净源码和 Preview 规则。正式包要求干净提交且当前有无关修改时，可从已授权的目标提交隔离构建；未提交的目标修复不能因此被遗漏，也不能为满足打包条件擅自提交或清理用户工作。临时构建空间不必成为额外交付目录。
- 保留已有 Preview 名称、Bundle ID 和数据隔离约定；普通产品新增运行时调试开关不意味着新增 Preview 身份或切换用户数据。

## 产物命名与架构

- 从已有版本事实源生成应用元数据，再让打包命名读取构建后的产品版本或同一生成值。保持界面、App、安装器和 DMG 中的产品版本一致，不新增平行的版本文件。
- 沿用项目确定的产品名和架构后缀，不追加随机值、提交号或 Debug／Release 后缀。同版本重建使用原交付路径；正式包与已有 Preview 包的命名区别保留。
- 从实际构建目标和二进制确认架构，不凭当前机器推断；没有需求时不扩成 Universal 包。架构读取服务于命名与交付说明，不再挂载产物重复读取比较。

## 单一入口的执行顺序

1. **构建并组装 App。** 使用本次目标源码构建 Release，写入版本，放入资源、动态库、helper 与安装载荷。
2. **由内向外签名。** 使用项目固定的 Apple Development 身份，先签嵌套代码，再签外层 App；保留各组件的 entitlements 等既有签名参数。按实际嵌套关系签名，不使用 `codesign --deep --force` 代替该顺序。构建工具已经完成的签名无需再加一轮；签名后不再改写载荷。
3. **封装 DMG。** 调用现有镜像创建命令，已有 DMG 签名在封装后执行。
4. **清理并报告。** 输出关键阶段和最终路径；各命令失败即停止，清理仍执行，不自动更换证书或降级签名。

构建成功代表已完整组装 App，签名与镜像工具的退出状态代表各自操作结果。外层不再执行产物存在性断言、重复验签、镜像回读或版本与架构比对。脚本缺少必要构建步骤时直接修复该步骤；发布版本与签名身份在版本准备或项目接入时确定。

已有入口覆盖这些步骤时直接执行，补齐缺失步骤即可。签名命令成功不等于已公证或已通过 Gatekeeper；本流程不自动增加 Developer ID 或公证步骤。签名顺序依据 [Apple 嵌套代码签名说明](https://developer.apple.com/library/archive/technotes/tn2206/)。

## 打包脚本与载荷

- 保持项目当前可靠的打包方式。已有简单 `hdiutil` 流程就复用，不因整理规范引入新的打包依赖、Finder 自动化或装饰性步骤；已有外观需求也不因简化而丢失。
- 将本次所需的 App、安装入口和必要资源放入独立暂存目录，不把整个 build／dist 目录作为镜像载荷。重新组装受本次脚本管理的载荷，防止旧 helper、旧资源、日志或临时文件混入。
- 同版本重打时，旧 DMG 视为过期产物，可以先删除，再直接生成到固定交付路径；不要求保留、备份或恢复旧包。临时输出仅按打包工具的实际需要使用，不为保住旧包增加流程。构建、签名或封装失败就返回失败并清理本次不完整产物，不能把旧包或半成品报告成本次成功。
- 临时名称只用于内部工作；脚本退出时清理自己创建的暂存目录和未完成镜像。过程文件的保留与清理按下节处理。
- 修改脚本时使用其声明的 Shell 运行验证，不用当前交互式 Shell 的成功代替。若依赖 macOS 系统 Bash，就兼容该环境；不要因本机安装了较新 Bash 而给 CI 引入隐含依赖。

## 过程材料与目录收尾

- 编译缓存允许保留在项目固定的缓存位置，复用现有机制，不按每次任务无限新建一份。已确认的下载缓存同样按项目策略复用；日志、检查结果、截图和中间 App 副本不能仅因可再次查看就称为缓存。
- 普通构建与检查默认使用命令输出和退出状态，不额外生成 build-info、探针 JSON、依赖快照、成功日志、截图档案或过程报告。确实需要文件作为本次检查输入或供智能体查看时可以临时生成，用完清理。
- 长期保留的非缓存文件应服务于产品运行、安装更新、发布渠道的实际需求，或用户明确要求交付的材料。应能说明谁在后续使用它、用来做什么；“已有脚本会生成”“将来可能排错”“证明智能体做过验证”都不足以成立。普通打包不额外生成一份保留理由清单。
- 简化已有流程时，优先删除无实际用途的生成步骤及其专属留档检查，将输入决策放在执行前，保留实际操作的错误传播与清理；不要仅把冗余文件移入隐藏目录或增加 `.gitignore` 来掩盖积累。
- 本次产生的暂存、重复 App、截图和过程结果，使用结束后由脚本或智能体自行收尾，不留给用户逐项要求删除。交付输出区域保留当前交付物及确有用途的附件；构建完成的判断应包括收尾，而不只检查 DMG 是否存在。
- 为尚未解决的具体故障可以暂留必要诊断，简要说明它支撑哪个问题；问题解决后清理。任务中断不等于这些文件永久有用，恢复任务时继续完成收尾。失败时保留必要错误信息即可，不默认归档整个工作目录。
- 清理对象限于归属明确的生成物，先确认没有仍在运行、挂载或使用；不因目录叫 build／dist 就删除未知文件，不动用户配置、历史、词库、源文件或仍需复用的缓存。安全边界用于识别对象，不作为无限保留已确认过程垃圾的理由。

## 安装方式

- 普通拖放式 App 沿用 App 加 Applications 入口；输入法、扩展或其他专用产品沿用其安装器和目标位置。不能把所有 DMG 都改成拖入 Applications。
- 保留必要的许可证、源码附件和安装说明；只删除无用生成物，不能把已有分发要求当作杂物清掉。安装说明应对应真实载荷和更新方式。
- 安装更新涉及替换时，使用本次成功构建的载荷，沿用项目已有的失败恢复机制并保留用户数据；旧进程未安全退出或目标仍占用时报告具体问题，不强制清缓存、删除数据或改系统设置来掩盖失败。

## 开发验证与日常交付

- 创建、适配或修改打包逻辑后，用一次实际产物验证实现：运行 `hdiutil verify`，挂载检查内部签名、版本、架构和安装入口；安装器检查实际安装载荷。使用结束后卸载并清理。验证失败应修复负责该结果的步骤，不把这套开发验证留在日常执行路径中。
- 修改打包脚本后，在隔离输出中实际覆盖成功打包、同版本重打和关键失败路径；确认成功后无多余过程残留，失败被正确报告并清理本次半成品。旧 DMG 是否保留不作为验证要求。不要只做 Shell 语法检查。
- 没有可用证书、依赖或真实构建条件时，明确未验证范围，不创建一个未签名包冒充成功；针对改动选择必要检查，不重复执行整套与本次无关的验证。
- 日常打包执行已验证入口并读取日志、退出状态，不在脚本成功后人工重跑同一批验证。安装／替换按已获授权执行；修改安装机制后再验证进程路径与新产物一致。DMG 生成不等于已安装或用户已验收。
- 在回复中给出最终路径、产品版本、构建配置、架构、实际签名／公证状态和已完成验证。校验和、构建来源等只有在实际发布机制或用户交付要求需要时才额外保存文件，不能仅因历史脚本已经生成就永久沿用。
