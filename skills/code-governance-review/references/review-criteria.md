# 代码结构与治理专项审查准则

本准则只服务于代码结构和代码治理判断，不是通用 code review 检查表。根据当前业务切片选择适用项，不机械穷举。

## 发现成立条件

一项发现需要同时具备：

1. 可定位的代码、配置、契约或调用链证据；
2. 与当前业务职责、调用关系或真实变化轴的明确联系；
3. 可说明的结构、维护或扩展影响；
4. 项目规则、官方规范或可解释工程原则中的判断依据。

只有个人风格偏好、假想未来需求或设计模式名称，不构成发现。

## 业务理解

只建立支持结构判断所需的业务切片：

- 业务目标和主要入口；
- 核心调用链及每层承担的职责；
- 关键数据由谁创建、维护和消费；
- 稳定业务规则与已经存在的变化点；
- 对当前结构有约束作用的公开契约或兼容要求。

整体业务逻辑是指被审查业务范围内的完整逻辑，不等于默认扫描整个仓库。

## 审查维度

### 职责与分层

- 业务概念是否有清晰、稳定且一致的代码表达；
- 表示、编排、业务决策、持久化和外部集成职责是否合理归属；
- 一个组件是否承担多个独立变化原因；
- 同一业务规则是否散落在多个无保护位置；
- 通用组件是否混入特定业务策略，或业务模块是否重复公共机制。

### 依赖与边界

- 依赖方向是否与业务所有权一致；
- 是否存在循环依赖、反向穿透、内部模型泄漏或绕过既有边界；
- 接口、DTO、事件和存储模型是否承担了不属于自己的职责；
- 外部协议或供应方差异是否污染稳定业务逻辑；
- 生命周期和资源所有权是否因结构不清而分散。

### 可维护性

- 命名、结构和控制流是否表达业务意图，而不仅是技术步骤；
- 修改一个业务规则是否需要同步编辑多个不相关位置；
- 重复分支、散落常量或隐式约定是否容易造成规则分叉；
- 结构是否便于定位变化影响并进行局部验证；
- 注释和文档是否掩盖或违背实际职责边界。

### 可扩展性

只针对已有多个实现、配置选择、供应方差异、兼容要求或已确认需求等真实变化轴进行判断。

- 稳定规则是否与频繁变化的策略、协议或数据源耦合；
- 新增一个已知同类变体是否需要修改大量无关代码；
- 扩展点是否保持清晰的类型、职责和生命周期约束；
- 抽象带来的复杂度是否低于继续使用直接代码的成本。

### 工程规范与治理

- 是否违反目标目录适用的 `AGENTS.md`、项目约定或已启用工具规则；
- 命名、包/模块组织、依赖管理和公开接口演进是否一致；
- lint、格式化、静态分析或依赖规则是否存在与本次结构直接相关的治理盲区；
- 项目没有明确规则时，语言/框架官方规范和主流实践是否提供了适用依据。

不能仅凭外部流行写法把项目现状判为问题。项目约定本身产生可证明的结构成本时，分别说明“符合现有约定”和“约定带来的影响”。

## 设计模式门槛

设计模式只用于回应已存在的结构压力。

| 候选机制 | 适用信号 | 不应采用的情形 |
|---|---|---|
| 策略 | 存在多个真实算法或政策，并由明确规则选择 | 只有单一实现或简单输入校验 |
| 工厂 | 创建过程随真实类型变化，且依赖或生命周期需要统一约束 | 只是隐藏一次简单构造 |
| 注册表 | 需要按稳定标识发现多个实现，并有明确注册和冲突规则 | 固定少量分支或集合可能无界增长 |
| 状态模型 | 状态迁移和非法转换构成核心业务结构 | 只有互不关联的条件判断 |
| 适配器 | 外部协议差异需要与稳定业务模型隔离 | 只增加没有隔离价值的转发层 |

提出模式时，同时给出当前结构压力、最小非模式方案、模式收益、新增复杂度和适用边界。简单提取、明确数据模型或职责调整足够时，不升级为模式。

## 非专项事实的使用边界

功能错误、安全风险、性能瓶颈、并发/事务问题、内存问题和测试缺口不作为独立搜索目标。仅在它们能够直接证明下列结构问题时引用：

- 职责放置错误；
- 模块或数据边界泄漏；
- 依赖、变化或生命周期没有被隔离；
- 同一业务规则因结构分散而不一致。

输出时仍然陈述结构根因和治理影响，不扩展为对应领域的完整审查结论。

## 发现类型

- **结构问题**：职责、分层、依赖或边界已经造成可证明的维护或演进问题；
- **治理风险**：当前可工作，但真实变化下的维护或扩展成本已经显现；
- **改进建议**：结构收益明确，但不影响当前业务成立；
- **待核验项**：存在结构线索，但缺少完成判断所需的业务或代码事实。

不建立通用 code review 的阻断/严重性体系。按对当前业务维护和演进的实际影响排列发现。

## 推荐输出

1. 总体专项结论；
2. 审查范围和业务理解；
3. 按影响排序的结构问题、治理风险和改进建议；
4. 已检查但未形成问题的关键结构；
5. 未覆盖范围和证据边界。

每项发现包含精确位置、业务关系、直接证据、结构性影响和最小治理方向。不要粘贴大段代码，也不要把未执行的测试或运行验证表述为通过。
