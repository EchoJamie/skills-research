# 第三批设计决策

> 记录日期：2026-08-13<br>
> 状态：以下内容已经逐项获得用户确认，是当前技能组设计基线；首版技能已于同日依据本基线制作在 `skills/` 下。<br>
> 与此前文档的关系：本文件承接 [03-第二批设计决策.md](03-第二批设计决策.md)，并记录对 [05-第二轮对抗复核与修正建议.md](05-第二轮对抗复核与修正建议.md) 的逐项确认结果。与此前决策或建议冲突时，以本文件为准。

## 1. 核心技能组收缩为两个技能

| 编号 | 决策 |
|---|---|
| D-48 | 第一版核心技能组只包含“实施规划”和“独立审核”两个技能。 |
| D-49 | 取消任务执行技能。开发工具包必须足够自包含，使普通新会话或新智能体不依赖额外技能即可直接读取和执行。 |
| D-50 | 用户可以在新会话中直接提供开发工具包路径，由执行智能体根据事实性前置依赖自行安排执行；需要时可以使用子代理，用户明确要求且环境满足时可以使用现有 Herdr 技能。 |

任务执行仍然是开发工具包的使用阶段，但不是当前技能组需要制作的能力。如果以后真实使用证明不同智能体在整包调度、状态汇总或失败恢复上持续不稳定，再单独评估是否需要可选的执行协调技能。

## 2. 独立审核的两种显式触发方式

| 编号 | 决策 |
|---|---|
| D-51 | 独立审核技能只允许显式触发，不根据普通“看一下”“分析一下”或非正式评价隐式运行。 |
| D-52 | 正常情况下，由实施规划技能创建符合独立性要求的审核子代理，并在委托内容中显式调用独立审核技能。 |
| D-53 | 无法自动创建合格审核者时，实施规划技能生成一段可复制到新会话的审核交接提示词；提示词显式调用独立审核技能并包含最小充分上下文。 |

正式制作时，独立审核技能应配置：

```yaml
policy:
  allow_implicit_invocation: false
```

审核交接提示词是异常或人工跨会话交接内容，不必固定生成一份正式文档。用户复制提示词到新会话完成审核后，再回到原流程继续。

## 3. 子代理能力检查与失败出口

| 编号 | 决策 |
|---|---|
| D-54 | 实施规划技能委托审核前必须检查当前环境是否具备创建独立审核智能体的能力，不能把技能已安装等同于子代理一定可用。 |
| D-55 | 能创建子代理但只能继承规划会话完整上下文时，该结果只能作为辅助复核，不能通过独立审核门。 |
| D-56 | 子代理不可用、启动失败、超时或没有创建有效审核记录时，主流程停在“待独立审核”，不得用规划者自检替代，也不得继续生成《目标与实施边界》。 |

该停止属于异常阻塞，不是新增的常规用户确认断点。

## 4. 独立审核使用最小充分上下文

| 编号 | 决策 |
|---|---|
| D-57 | 独立审核只接收完成当前审核所需的最小充分上下文，不继承与审核无关的完整规划会话。 |
| D-58 | 审核输入应包括审核类型、被审核对象、规范性来源、允许核验的事实性来源、排除来源、审核记录输出目录、写入边界、通过条件和返回格式。 |
| D-59 | 规划者的自检结论、预期审核结果、已怀疑问题和拟定修复在独立审核完成前保持隔离，不提供给审核者。 |
| D-60 | 方案复审必须读取当前方案版本、上一轮审核记录和实际用户修改意见，既检查旧问题是否关闭，也重新检查新引入问题。 |

用户已经明确表达的修改意见属于规范性来源，不是普通历史讨论。审核所需信息不足时，审核者应报告缺失内容及其影响，不得猜测或默认通过。

## 5. 送审对象一致性校验

| 编号 | 决策 |
|---|---|
| D-61 | 每一轮审核开始时记录被审核文件、版本和送审摘要；审核结束时再次校验。 |
| D-62 | 单一方案文档使用文件摘要；开发工具包按稳定文件的相对路径和内容计算整体摘要，审核记录、执行记录和临时文件不参与计算。 |
| D-63 | 同一轮审核开始到结束期间，被审核对象不得变化。两次摘要不一致或审核者越界修改被审核对象时，本轮审核失效，必须重新送审。 |

该校验不要求 Git 提交，也不要求复制方案或工具包目录。开发工具包可以在不同审核轮次之间更新，但一轮审核进行期间必须保持稳定。

## 6. 《实施方案与计划》的版本与确认记录

| 编号 | 决策 |
|---|---|
| D-64 | 《实施方案与计划》采用版本化管理；实质修改形成新版本，旧版本继续保留，用于比较审阅版本之间的变化。 |
| D-65 | 请求用户确认方案基线时，必须明确提供方案路径、版本、内容摘要和确认范围。 |
| D-66 | 用户明确确认后，由实施规划技能在“方案审核记录”目录创建“用户确认方案基线”记录，持久化方案路径、版本、内容摘要、确认时间、确认范围和保留事项。 |
| D-67 | 独立审核文件由审核者创建；用户修改意见和用户确认方案基线由实施规划技能根据用户的明确表达记录。实施规划技能不得将模糊回复或无回复解释为确认。 |
| D-68 | 已确认的方案版本保持不变。后续发现实质方案问题时，只能报告并由用户决定是否重新打开方案；获得允许后生成新方案版本并重新经过独立审核和用户确认。 |

方案是否已确认以外部确认记录为准，不在用户确认后再修改方案正文写入“已确认”状态，以免改变用户实际确认的内容摘要。

## 7. 开发工具包的性质和生命周期

| 编号 | 决策 |
|---|---|
| D-69 | 开发工具包是不包含实际代码的开发计划和任务规格，只描述实现目标、事实、约束、依赖、停止条件和验收要求。 |
| D-70 | 生成开发工具包时不得修改业务代码、生成可直接应用的代码补丁、正式迁移文件、配置改动或其他实际实现产物。 |
| D-71 | 开发工具包不保留历史版本，始终只维护当前有效内容；在内部“生成、自检、审核、修改、复审”循环的审核轮次之间，可以更新、覆盖或重新生成。 |
| D-72 | 工具包审核期间发现已经确定的方案存在问题时，审核者和实施规划技能都不得修改方案；必须将其归为方案问题，报告并停止当前工具包审核。 |
| D-73 | 用户决定重新打开方案并确认新版本后，可以直接修改或重新生成当前开发工具包；不保留旧工具包副本，并重新对整个工具包执行自检和独立审核。 |

开发工具包可以包含目标模块、仓库内相对路径、符号名、行为契约、数据结构、伪代码级说明、实施步骤和验证命令，但不能提前完成实际代码开发。

## 8. 审核发现、归属和最终结论

审核发现统一分为：

| 分类 | 含义 | 流程影响 |
|---|---|---|
| 阻断问题 | 不处理就会违反需求、方案基线、工程事实、安全边界或验收闭环 | 审核不通过 |
| 非阻断风险 | 当前产物仍然正确、完整且可执行，但执行时需要控制或持续关注 | 可以通过，但控制措施必须落实到相关任务 |
| 改进建议 | 不影响当前正确性、完整性和可执行性的优化 | 可以通过，可选择采纳 |

| 编号 | 决策 |
|---|---|
| D-74 | 每个发现还必须标明问题归属：方案问题、开发工具包问题或事实阻塞。 |
| D-75 | 方案问题在开发工具包审核中一律视为阻断，只报告、不修改方案。 |
| D-76 | 审核结论只允许“通过：没有未解决阻断问题”和“不通过：存在未解决阻断问题”两种。 |
| D-77 | 影响核心判断的未验证范围属于阻断，不能降级为非阻断风险；审核者也不得为了结束循环而降级反复出现的问题。 |

非阻断风险不能只留在审核记录里，必须落实到相应任务的约束、停止条件或验收要求。改进建议不得扩大已确认方案范围。

## 9. 修订循环的进展熔断

| 编号 | 决策 |
|---|---|
| D-78 | 不设置开发工具包的总审核轮数上限；只要发现能够在已确认方案内解决且修订取得实质进展，就继续自检和复审。 |
| D-79 | 同一根因经过两次开发工具包修订后仍是阻断问题时，停止自动循环。 |
| D-80 | 已解决问题再次出现、规划者与审核者对规范性来源存在实质分歧、缺少权威事实或权限、修正要求改变方案、反复无法形成稳定送审对象，或者只能靠降低验收与缩小既定范围通过时，均触发熔断。 |
| D-81 | 熔断后保留审核记录，向用户报告问题根因、已采取的处理、仍然阻断的原因以及所需事实或决定；在阻塞解除或用户作出决定前，不得降级问题或继续修改方案和工具包。 |

“实质进展”必须表现为缺失任务已补齐、冲突边界已消除、验收已经可判定、依赖已经具有事实性出口，或者原阻断范围发生可验证的缩小，不能只改变措辞。

## 10. 长周期执行中的代码基线漂移

| 编号 | 决策 |
|---|---|
| D-82 | 每份执行任务单在逻辑上区分“规划时现状”“前置任务出口事实”和“开工时复核项”，但不强制采用完全相同的章节标题。 |
| D-83 | 前置依赖不能只写某任务已完成，还必须说明当前任务开工前应真实存在的结果和验证证据。 |
| D-84 | 只有文件位置、类名、行号或内部实现方式变化，而任务目标、边界和验收不变时，执行者可以重新定位后继续，只需在执行结果中简略记录变化。 |
| D-85 | 前置依赖未达成时停止并报告；变化影响任务目标、修改范围、依赖或验收时，返回实施规划流程更新当前开发工具包并重新审核；发现方案问题时只报告，不修改方案。 |

行号只能作为定位提示，不能作为修改授权。后置任务不得虚构前置任务完成后的具体文件结构。

## 11. 正式产物与审核过程材料分离

| 编号 | 决策 |
|---|---|
| D-86 | 方案审核记录、开发工具包审核记录和正式开发工具包分别保存。开发工具包审核记录不得放在开发工具包目录内。 |
| D-87 | 开发工具包审核记录可以留存，但属于开发工具包最终定稿前的过程材料；独立分享工具包时不自动包含这些记录。 |
| D-88 | 开发工具包必须能够独立分享和执行，不能要求接收者同时取得《实施方案与计划》或审核记录。工具包可以记录来源方案版本和摘要，但只能作为来源标识，不能成为执行依赖。 |
| D-89 | 工具包不得写入规划环境的绝对路径；代码定位使用仓库内相对路径、模块名和符号名。 |

当前建议的正式产物结构为：

```text
<功能规划目录>/
├── 实施方案与计划_v1.0.md
├── 实施方案与计划_v1.1.md
├── 方案审核记录/
├── 开发工具包/
│   ├── README.md
│   └── 任务-*.md
├── 开发工具包审核记录/
└── 目标与实施边界.md
```

阶段目录或任务二级目录仍然由实际方案复杂度决定，不强制生成。分享方案时可以只分享对应版本的《实施方案与计划》；分享工具包时只分享 `开发工具包/`。

## 12. 当前完整工作流

```text
读取已经确定的需求和项目规则
          ↓
核验当前代码与工程事实
          ↓
生成或修改《实施方案与计划》版本
          ↓
实施规划技能自检
          ↓
显式委托独立审核技能
  ├─ 自动创建合格审核子代理
  └─ 不可用时生成可复制到新会话的审核提示词并停止等待
          ↓
根据审核记录修订方案并继续复审
          ↓
没有未解决阻断问题
          ↓
用户确认具体方案版本和内容摘要          ← 唯一常规用户确认断点
          ↓
记录“用户确认方案基线”
          ↓
生成当前开发工具包（只生成计划，不开发代码）
          ↓
实施规划技能自检
          ↓
显式委托独立审核技能审核开发工具包
          ↓
工具包问题 ──→ 修改或重新生成工具包 ──→ 重新自检、复审
方案问题   ──→ 只报告并停止，由用户决定是否重新打开方案
          ↓
没有未解决阻断问题
          ↓
生成《目标与实施边界》并执行最终一致性检查
          ↓
规划流程结束
          ↓
用户在新会话中直接提供开发工具包路径并执行
```

## 13. 正式制作阶段的落地结果

以下实现细节已在首版制作和前向测试中按本基线落地，不新增设计确认断点：

- 实施规划技能：`skills/feature-implementation-planning/`。
- 独立审核技能：`skills/feature-planning-review/`，界面策略明确禁止隐式触发。
- 两个技能各自包含可独立复制的 `SKILL.md`、界面元数据、参考协议/模板和相同的摘要脚本。
- 目录摘要覆盖目标目录内全部普通文件；审核记录位于工具包外，因而不需要主观排除规则；发现符号链接或特殊文件时摘要失败并报告。
- 方案、工具包、审核记录、跨会话审核交接和最终总结均已形成首版模板。
- 技能目前只保存在研究目录内，尚未安装到 Codex 的个人或项目技能目录；安装和分发方式留待真实使用前决定。
