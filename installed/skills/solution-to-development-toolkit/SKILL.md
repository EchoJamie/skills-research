# 方案转开发工具包

## 目标

把已确认方案转换为不依赖规划会话隐含上下文的开发工具包。任务包是明确结果、边界、依赖和验收的委托契约，不是替领取者规定实现路径的操作手册。任务包之间只表达真实前置条件，不设置人为的全局顺序或并行组；满足前置条件且写入范围不冲突的任务可以独立领取。

本技能只生成和修订文档，不修改业务代码，不执行任务，也不替用户改变已确认方案。

## 开始条件

1. 读取工作区规则、已确认方案和支撑方案的当前代码事实，区分用户决策、事实、假设与待确认事项。
2. 确认方案目标、边界和关键决策已经关闭。若仍需丰满方案，返回方案细化；若仍包含多个独立目标或多条主线，先返回目标或阶段拆分。
3. 按项目规则确定一个专属的 `<功能主题>开发工具包/` 目录。
4. 确认项目级 `toolkit_architect` 可用；方案涉及前端、客户端或其他用户终端时，还必须确认 `interaction_designer` 可用。缺少必需角色时停止并报告，不能用普通代理静默替代。
5. 读取 [references/task-package-template.md](references/task-package-template.md)。

## 相邻技能

- 上一阶段是 `solution-refinement`。若方案的目标、整体步骤、必要设计、验收目标或关键决策尚未关闭，返回上一技能继续细化；若问题来自目标过大，再由上一技能衔接 `solution-step-alignment`。
- 当前方案系列尚未定义本技能之后的技能。开发工具包完成一致性检查后停在本阶段边界，不自动领取或执行任务包。

## 角色与文档所有权

- `toolkit_architect` 负责开发工具包 `README.md`、任务包结构、依赖关系和全部任务包文件。
- `interaction_designer` 仅在涉及用户终端时启用，负责 `交互设计.md`；可以只读检查终端任务包，但不直接修改架构师拥有的文件。
- 主对话拥有最终整合权。专业代理结束写入后，主对话可以修改全部交付文档，但不得让两个代理并发修改同一文件。
- 两个专业代理只允许写主对话明确分配的文档路径，不修改业务代码、Git 状态或其他文件。

## 专业代理创建方式

- 使用项目 `agent.toml` 注册的 `toolkit_architect` 和 `interaction_designer` 创建独立的新子代理会话，不使用 fork 或其他继承主对话历史的创建方式，也不以普通代理模拟专业角色。
- 每次创建消息先明确本轮角色身份，再提供主对话整理的最小充分交接、具体任务、输入文档、输出路径、文件所有权和期望出口。角色的稳定职责以对应 `agent.toml` 为准，创建消息不重复整份角色说明。
- 命名自定义代理不可用时，按开始条件停止并报告，不降级为 fork 的普通代理。

## 协作流程

### 1. 建立共同基线

主对话先形成一份最小充分交接，包含确认方案、已确认决策、当前事实、项目规则、输出目录、各角色文件所有权和本轮期望结果。不要把一个代理的结论预先当成另一个代理必须接受的事实。

### 2. 并行形成第一轮草案

在职责互不冲突时，同时委托：

- `toolkit_architect`：创建消息先说明“你在本轮以 `toolkit_architect` 开发工具包架构师身份工作”，再要求其分析方案覆盖、任务包边界、事实性依赖和工具包结构，写入架构师拥有的草案文件。
- `interaction_designer`：创建消息先说明“你在本轮以 `interaction_designer` 交互设计师身份工作”，再要求其分析终端用户场景和当前实现，写入 `交互设计.md`。不涉及用户终端时不启动该角色。

等待所有已启动角色完成，不在结果返回前提前定稿。

### 3. 主对话分析整合

主对话必须读取实际文档和代理结论，核对事实、覆盖、边界和冲突，不能充当传声筒或原样转发意见。

- 先判断分歧属于事实错误、职责越界、设计缺口还是用户关键决策。
- 能由已确认方案和事实确定的内容，主对话直接收束并向对应角色下发具体修订要求。
- 任务包责任和依赖结构由主对话结合方案与事实自行收束；只有事项会改变已确认的目标结果、整体达成路径、关键用户流程或方案实质边界时，才升级为关键决策，至少给出两个真实可行方向及影响并等待用户决定。
- 后续委托必须包含主对话自己的判断、待解决问题和期望出口，不使用“另一个代理说……”代替分析。

### 4. 收敛任务包

关键事项关闭后，让架构师依据稳定的交互设计完善任务包和依赖关系。交互设计师随后只读检查终端相关任务包，主对话分析其反馈，再自行修订或要求架构师定向修订。

主对话负责在每个终端任务包中补充并核对：

- `交互设计依据`的相对路径和具体章节；
- 本任务包实际需要落实的用户流程与交互状态；
- 对应的交互验收要求；
- 与其他终端场景的边界。

不能只放一个笼统的交互设计文档链接。交互设计变化后，重新检查所有引用受影响章节的任务包。

### 5. 完成一致性检查

完成前由主对话检查：

- 方案中的每项实质目标和约束都有任务包或工具包级落实位置；
- 每个任务包都有独立结果、清楚边界、必要的任务特有事实与约束，以及可判断的验收；
- 所有前置条件都指向可观察的完成出口，而不只是任务编号；
- 没有用编号、目录顺序或人工分组暗示不存在的全局顺序；
- 终端任务包已经吸收相关交互设计和验收要求；
- 没有用详细步骤、文件清单、普通检查或通用规则替领取者完成实施设计；
- 每个任务包都明确验收由领取 agent 自行执行；所有指定检查和领取者为覆盖实际改动选择的必要检查必须全部通过，未执行或未通过的必需验收不能记为完成；
- 工具包没有包含业务代码、补丁或未经确认的新方案设计。

检查通过后结束，不开始开发。

## 任务包拆分原则

- 创建者负责把问题划清楚，领取者负责把问题解决掉。任务包对结果、边界、硬前置和验收保持明确，对实现路径、具体文件、包内步骤和普通技术检查的选择保留执行者自主空间，但不免除其自行完成验证的责任。
- 一个任务包原则上只覆盖一个业务场景、一块完整功能，并有可独立判断的结果。
- 不按文件、类、接口或技术层机械拆分；技术层只有在形成独立结果和真实前置出口时才能独立成包。
- 一个任务包出现多个独立入口、用户目标、状态体系或验收结果时，优先回查上层方案拆分，不能靠增加篇幅掩盖问题。
- 同一连续场景内的弹窗、抽屉、步骤页或结果页可以保留在一个任务包；页面数量本身不是拆分标准。
- 任务包内部可以有必要顺序；任务包之间只记录硬前置条件。编号仅用于识别，不代表执行顺序。
- 前置条件已满足且写入范围不冲突时，任务包才具备并行执行条件；不要为了展示并行而预设并行组。
- 只写遗漏后会改变方向的非显然事实、既定契约和任务特有风险。通用执行、评审和证据口径放在工具包 `README.md`，不在每个任务包重复。
- 能由 agent 自动执行的验收不设为人工卡点，只有关键决策或新增授权交还用户。必需外部条件不成立时立即暂停并报告影响与缺口，不自动重试、不等待状态变化；除非恢复条件本身需要用户作出关键决策或新增授权，否则不把阻塞包装成用户决策。无法执行的必需验收必须标为未验证或阻塞，不能宣称通过。

## 开发工具包

```text
<功能主题>开发工具包/
├── README.md
├── 交互设计.md              # 仅涉及用户终端时生成
└── 任务包/
    └── <任务包标识>-<名称>.md
```

`README.md` 应说明来源方案、总体目标、范围、共同决策与约束、任务包索引、事实性依赖关系、可领取条件、总体验收，以及所有任务包共用的执行、评审和证据口径。共享契约只有在多个任务包确实共同依赖时才单独成文，不预建空目录或占位文件。

每个任务包应当能够独立理解目标并开工，不要求执行者重新阅读完整方案。包内只写相关决策、必要事实、边界、硬前置和验收；除非方案或契约已经固定，不规定详细实施步骤。领取 agent 自行选择足以覆盖实际改动的检查并负责全部跑通。项目特有的执行者、评审、分支、人天等字段按项目规则或用户要求填写。

## 边界

- 专业代理可以发现问题和提出方向，但只有主对话与用户关闭关键决策。
- 不新增默认测试、安全、审核或其他专业角色；真实使用证明存在持续缺口后再决定是否增加。
- 不运行构建、测试、部署、Git 写操作或外部系统变更来代替文档规划。
