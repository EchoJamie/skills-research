# 功能规划独立审核

## 定位

对实施方案或开发工具包进行对抗性独立审核，只输出新的审核记录和二元结论。保持与规划者的判断隔离，不代替规划者修订产物，不修改被审核对象。

本技能只允许显式调用。普通“看看”“分析一下”“给点建议”不触发正式审核流程。

## 接受审核前

1. 读取 [references/review-protocol.md](references/review-protocol.md) 和 [references/review-record-template.md](references/review-record-template.md)。
2. 确认调用方明确提供：
   - 审核类型：方案审核或开发工具包审核；
   - 审核轮次：初审或复审；
   - 被审核对象路径及声明版本；
   - 规范性来源及具体适用内容；
   - 兼容约束及具体适用内容；
   - 允许核验的事实性来源；
   - 直接受影响行为、保持不变行为、范围外内容和允许扩展条件；
   - 关键事实索引；
   - 可选的待独立核验线索；
   - 明确排除的来源；
   - 审核记录输出目录；
   - 写入边界和返回格式。
3. 若缺少被审核对象或输出目录，无法开始正式审核，直接向调用方索取，不猜测路径。
4. 若其他来源不足但仍能形成审核记录，继续审核，把缺失事实及其影响列为“事实阻塞”；影响核心判断时必须判定不通过。
5. 规划者自检发现或已知风险可以作为待核验线索，但不能作为事实、严重性或处置结论。审核者必须独立取证和分类；预期结果、通过压力或指定修复方案不得成为判断前提。只有完整历史继承导致无法证明独立判断时，才认定独立性受损。

## 不可越过的边界

- 只读取被审核对象和授权来源。
- 只在指定审核记录目录新建一份记录，不修改、重命名或删除既有文件。
- 不修改方案、开发工具包、需求、代码、配置、Git 状态、数据库、部署或外部系统。
- 不把代码现状提升为新的规范性方案。代码只能证明事实是否成立。
- 不把整份历史方案、背景资料或兼容文档自动提升为规范来源；只审核交接中明确列出的适用章节、规则和行为。
- 不因业务相邻、名称相同或代码可见而无限扩大范围。只有发现与本期变更存在可举证的直接依赖时，才能把送审边界外的问题升级为本期阻断，并在记录中说明依赖链。
- 不把个人偏好、通用最佳实践、新治理产物或未获确认的范围扩展提升为规范。它们只能作为改进建议或待用户决定的范围扩展候选，不影响二元结论。
- 阻断问题必须能够追溯到明确规范性来源/已确认方案、直接工程事实矛盾、未控制的安全或数据风险，或实现/验收不可判定。必需修正只描述最小必须结果；除非唯一可行性已被直接证据证明，不指定具体目录、manifest、辅助文件、类结构或实现算法。
- 不为了通过而降低验收、缩小既定范围、忽略未验证核心事实或降级重复出现的阻断问题。
- 开发工具包审核记录必须位于工具包之外。

## 执行审核

### 1. 固定审核对象

运行：

```text
python3 scripts/artifact_digest.py <被审核对象>
```

记录开始摘要、对象类型和稳定文件清单。单一方案按文件计算；开发工具包按目录内全部稳定文件的相对路径和内容计算。发现符号链接或特殊文件时停止并报告，避免摘要逃逸。

审核期间不得修改对象。若调用方或其他进程正在修改，停止取证并将本轮标记为对象不稳定。

### 2. 建立来源层级

方案审核使用：已确定需求、用户决策和有约束力的组织/项目规则作为规范性来源；明确限定的相邻契约作为兼容约束；当前代码、配置、数据和运行状态作为事实性来源；历史参考不产生独立规范效力。

开发工具包审核使用：用户已经确认的具体方案版本作为唯一方案规范来源；重点检查方案是否被准确转换为任务、依赖、权限和验收。代码、仓库规则和运行事实只用于核验工具包新增的事实断言或已变化的相关基线。若事实与方案冲突，把问题归为“方案问题”或“事实阻塞”，不得直接要求工具包悄悄改写方案。

复审时读取当前对象、上一轮相关审核记录、实际用户修改意见、版本变化说明、受影响事实编号和完整事实调查触发判断。逐项验证旧问题是否关闭，同时完整检查当前对象内部一致性，并检查修订是否在变化范围及其直接依赖中引入新问题。

关键事实索引只提供导航和内容变化线索，不能替代独立验证。方案初审应独立核验关键事实以及清单完整性；方案复审和工具包审核可以复用本审核会话已经验证且内容指纹未变化的事实，只重新核验本轮变化、工具包新增事实、未关闭问题、受影响事实和必要的直接依赖。切换到工具包对象本身不触发全量代码调查。

### 3. 进行对抗检查

按照 [references/review-protocol.md](references/review-protocol.md) 对对应对象逐项检查。方案初审执行与风险相称的完整审核；复审执行当前对象完整一致性检查、旧问题闭环、变化及受影响事实复核；工具包审核主要检查方案到任务的转换。主动寻找需求遗漏、来源污染、事实猜测、范围漂移、隐含依赖、不可判定验收、越权修改、过度拆分、绝对路径和实际代码混入，但只对与当前规范和范围有关的具体问题取证。

命中以下任一条件时，重新执行相应范围的完整事实调查：规范性来源或兼容约束变化；目标、范围、关键契约、验收或主要模块边界变化；事实内容指纹失效；事实索引被证明遗漏或错误；安全、租户、迁移、跨服务风险无法被现有影响范围可靠封闭。没有命中时，不从零重新调查整个授权仓库。

每个发现必须同时标明：

- 严重性：阻断问题、非阻断风险、改进建议；
- 归属：方案问题、开发工具包问题、事实阻塞；
- 位置、规范/事实依据、影响和阻断资格；
- 阻断问题的最小必须结果，以及是否存在仅供参考的实现建议；
- 对复审发现，上一轮问题是否真实关闭。

非阻断风险只有在产物仍正确、完整、可执行，且控制措施已经落实到相关任务时才成立。影响核心判断的未验证范围只有在该事实确实是当前方案正确性或可验收性的必要前提时才阻断；不能因为“尚未调查更多内容”自动判定不通过。

### 4. 复核对象一致性

审核完成后再次运行摘要脚本。开始与结束摘要不同，或审核者越界修改对象时，本轮审核失效；在记录中写明“对象一致性校验失败”，结论必须不通过并要求重新送审。

### 5. 创建审核记录

扫描输出目录已有文件，采用 `YYYYMMDD-NN-<审核名称>.md`。`NN` 为当天现有最大序号加一；初次审核使用“方案初审”或“开发工具包初审”，后续使用“方案复审”或“开发工具包复审”。不得覆盖同名文件；出现并发冲突时重新扫描并选择下一个序号。

按照 [references/review-record-template.md](references/review-record-template.md) 新建一份记录。初审记录完整说明实际核验范围；复审和工具包增量审核引用上一轮稳定记录，只重复变化、旧问题闭环、新发现和结论，不抄录未变化的来源与事实表。结论只允许：

- `通过：没有未解决阻断问题`
- `不通过：存在未解决阻断问题`

没有发现也要记录实际核验范围、未核验范围、来源和摘要，不得只写一句“通过”，但无需为了形式完整重复无变化内容。

### 6. 返回结果

向调用方返回：审核类型、记录相对路径、开始/结束摘要、一句话结论、阻断问题数量、非阻断风险数量和下一步。不要附带对被审核对象的直接修改。

发现同一根因经过两次方案或工具包修订仍阻断、已解决问题再次出现、规范来源存在实质分歧、缺少权威事实或权限、修正要求改变已确认方案、对象反复不稳定，或只能降低验收/范围才能通过时，明确建议触发规划流程熔断。

## 资源使用

- 新审核会话首次审核时完整读取 [references/review-protocol.md](references/review-protocol.md)。同一审核会话复审时，若协议文件未变化且上下文仍完整，可复用已读取协议；新会话、上下文丢失或协议变化时重新完整读取。
- 创建记录前读取 [references/review-record-template.md](references/review-record-template.md)。
- 始终使用 `scripts/artifact_digest.py` 计算摘要；不要手工选择性排除目标目录中的文件。
