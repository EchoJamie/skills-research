# 背景与需求

## 1. 背景

在大型功能开发中，需求文档或总体方案往往不能直接交给一个新会话中的智能体执行。执行者仍然需要自行推断：

- 需求与当前代码之间的真实差距。
- 哪些决策已经确定，哪些不能由执行者临时决定。
- 应该先做什么，后做什么，以及哪些条件构成前置依赖。
- 一个任务允许修改什么、禁止扩展到哪里。
- 什么证据足以证明任务已经完成。

方向 6 的方案、审核记录和开发工作包表明，可以在总体方案与代码执行之间增加一层结构化转换，将复杂方案整理成带有目标、边界、依赖和验收要求的独立任务单。

## 2. 需求定义

创建一组相互配合的 Codex 技能，用于将“已经确定的功能需求”结合项目当前事实，转换为：

1. 可供人类审阅和确认的实施方案与计划。
2. 由另一个智能体独立生成的方案审核记录。
3. 方案基线获得用户确认后生成的完整开发工具包。
4. 开发工具包经过自检和独立审核后生成的《目标与实施边界》人类可读总结。
5. 可交给新会话或新窗口中的智能体独立执行的详细任务单。

当前确认的核心技能组只包含“实施规划”和“独立审核”两个技能。任务执行不再制作专用技能；新的会话或智能体应当能够直接读取自包含的开发工具包并执行，必要时根据用户要求和运行环境使用现有的子代理或 Herdr 能力。

## 3. 触发时机

技能在以下情况触发：

- 功能需求、目标和主要范围已经确定。
- 需要根据当前代码、项目规范、技术约束和交付条件生成具体实施计划。
- 计划需要被分解成可交由其他新会话独立执行的任务。

不应在以下情况触发：

- 用户还在探索需求、比较产品方向或决定是否实现。
- 任务只是一个边界清楚的小修改，无需单独生成方案和多份执行任务。
- 用户要求的是问题探查、缺陷池盘点或运行故障诊断，而不是将已定方案转为实施计划。

## 4. 主要输入

- 已确定的需求、设计材料和用户决策。
- 当前代码、测试、配置、部署链路与运行约束。
- 工作区和仓库内的 `AGENTS.md`、工程规则、Git 与验证边界。
- 交付期、人力、发布节奏或其他已知约束。

## 5. 核心输出

技能组不强制固定目录层级，但应根据实际复杂度组合以下产物：

- 实施方案与计划。
- 方案或计划审核记录。
- 需要用户或专业负责人确认的事项。
- 包含索引和详细执行任务单的开发工具包。
- 开发工具包独立审核记录。
- 最后生成的目标与实施边界总结。
- 必要时分离保存的执行记录。

## 6. 执行任务单的使用方式

- 一份任务单主要交给一个新会话或新窗口中的智能体执行。
- 新会话不应依赖规划会话的隐含上下文；任务单必须提供足以开工、停止和验收的自包含信息。
- 任务单只表达事实性前置依赖，不指定并行组或预先安排并行执行。
- 执行时由协调智能体根据前置依赖是否达成、工作区状态和修改冲突风险决定是否并行。

## 7. 范围边界

当前首版技能不包含：

- 需求发现、产品方向比较和功能取舍。
- 类似“租户切换问题与处理待办”的探查型事项池。
- 自动调度或启动多个执行任务；实施规划技能只在方案或开发工具包审核时委托独立审核子代理。
- 直接修改业务代码、执行任务或代替新会话完成开发。
- 默认授权 Git 提交、推送、合并、部署或外部环境变更。
- 项目进度管理平台或长期任务状态管理。
