# 代码结构与治理专项审查

## 定位

本技能只审查代码结构和代码治理。先理解被审查范围内的完整业务逻辑，再判断结构是否准确承载业务职责、变化和演进；不把“代码能运行”当成可维护，也不做脱离业务的风格评分。

审查阶段保持只读，只给出有代码事实和业务影响支撑的治理建议，不修改被审查对象。

## 专项范围

纳入：

- 业务概念、职责和分层是否清楚且归属合理；
- 模块、类、接口和数据模型之间的依赖方向与边界；
- 业务变化是否被隔离，代码是否易于理解、修改和验证；
- 已有真实变化轴下的扩展成本；
- 项目规范、语言/框架官方规范和主流工程实践的适用情况；
- 设计模式是否有必要，以及简单方案是否已经足够。

不主动审查功能缺陷、安全、性能、并发、内存、事务、测试覆盖或运行运维问题。只有当这些事实直接证明职责错误、边界泄漏、耦合失控或演进困难时，才把它们作为结构与治理结论的证据；不扩展成对应专项审查。

## 开始前

1. 读取工作区 `AGENTS.md` 及目标目录内继续适用的规则。
2. 固定审查对象：变更集、提交、模块或业务链路，并记录明确排除项。
3. 建立足够完整的业务切片：业务目标、入口、主要调用链、核心数据及其所有权、关键职责和已经存在的变化轴。
4. 确认项目实际启用的规范和工具；项目没有规定时，再参考语言/框架官方规范和主流实践。
5. 普通审查只读取代码、配置、测试和 Git 历史，不运行会产生构建产物或改变外部状态的命令。

## 审查方式

1. 完整读取并使用 [references/review-criteria.md](references/review-criteria.md)。
2. 沿实际业务调用链确认职责、依赖和数据如何跨越边界，只扩展到能证明直接依赖的相邻代码。
3. 将业务变化点与代码变化点对应起来，判断一次业务修改是否会引发无关修改、重复实现或不受控分支。
4. 对照项目规范、官方规范和主流实践形成治理判断；通用实践与项目约定冲突时，分别说明现状和影响，不直接判定项目错误。
5. 只有存在真实结构压力时才建议设计模式，并同时比较更简单的局部整理或直接抽象。
6. 每项发现必须连接精确代码证据、相关业务逻辑和结构性影响。证据不足时列为待核验项，不写成已确认问题。

## 输出要求

先给专项审查结论，再给必要证据。默认在对话中返回，不创建报告文件，除非用户明确指定输出路径。

至少说明：

- 审查对象、纳入和排除范围；
- 对相关业务逻辑、调用链和变化轴的理解；
- 按实际影响排序的结构与治理发现；
- 每项发现的位置、业务关系、结构性影响、判断依据和最小治理方向；
- 建议设计模式时的适用信号、简单替代方案、收益和新增复杂度；
- 未覆盖范围及静态审查、测试、真实运行验证的证据边界。

没有达到发现门槛的问题不为凑数输出。若未发现有直接证据的问题，明确限定为“在本次业务和代码范围内未发现有直接证据的结构与治理问题”。

## 边界

- 不把本专项审查表述为通用代码质量、功能正确性、安全性、性能或测试充分性结论。
- 不自动扫描整个仓库，不把相邻系统的历史问题并入本次结论。
- 不以重写、换框架、统一风格或增加设计模式作为默认治理方向。
- 需要改变业务目标、公开接口、数据所有权或兼容承诺时，只说明影响并交由用户决策。
- 关键业务入口、代码或项目规范不可访问时，报告缺口对结构判断的影响，不用猜测补齐。
