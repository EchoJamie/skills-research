## 1. 设计结论

当前能力不应制作成一个包含所有角色的大技能，也不应按每份文档机械拆分技能。建议按职责和上下文隔离拆成三个技能：

| 角色 | 建议技能名 | 单一职责 |
|---|---|---|
| 实施规划者 | `plan-feature-implementation` | 核验项目事实，编制与修订《实施方案与计划》，协调独立审核，生成并自检开发工具包，最后生成《目标与实施边界》 |
| 独立审核者 | `review-feature-artifacts` | 在独立会话中审核指定的方案或开发工具包，自行创建审核记录，不修改被审核产物 |
| 任务执行者 | `execute-feature-task` | 在新会话中领取一份执行任务单，复核前置条件和当前事实，在授权范围内实施、自验收并返回执行结果 |

三个技能构成一个技能组。正式制作时先分别验证触发和职责，再决定是否打包为统一插件；研究目录继续保留创建过程，不直接充当正式技能目录。

## 2. 角色边界

### 2.1 实施规划者

实施规划者既是方案编制者，也是主工作流协调者，但不是独立审核者。

必须负责：

- 判断需求是否已经具备进入实施规划的条件。
- 读取项目规范并核验当前代码、测试、配置、数据与交付约束。
- 最先生成《实施方案与计划》，根据审核意见反复修订。
- 仅在方案审核没有未解决阻断问题后，请求用户确认方案基线。
- 根据已确认方案直接生成完整开发工具包，不先生成任务拆分草案。
- 对开发工具包执行结构和语义自检。
- 委托独立审核子代理审核开发工具包，并闭环处理实施层问题。
- 审核无阻断问题后，最后生成《目标与实施边界》。

不得负责：

- 把自己的自检称为独立审核。
- 替用户确认方案基线。
- 为了通过审核而静默改变已经确认的方案。
- 自动启动开发任务、提交代码、推送、合并或部署。

### 2.2 独立审核者

独立审核者必须运行在另一个会话或子代理上下文中。审核的独立性来自上下文隔离、来源限制和写入边界，而不只是角色名称不同。

必须负责：

- 从主流程指定的审核对象和来源清单重新建立上下文。
- 审核方案的事实依据、需求覆盖、内部一致性、实施可行性和未决事项。
- 审核开发工具包对已确认方案的覆盖、任务边界、前置依赖、验收可判定性和新会话自包含性。
- 在指定审核记录目录中自行确定文件名并创建一份新记录。
- 对当前审核对象给出“通过”或“不通过”的明确结论。

不得负责：

- 直接修改《实施方案与计划》、开发工具包或历史审核记录。
- 把历史方案、聊天记忆或自己的偏好提升为方案依据。
- 在开发工具包审核阶段重新设计已确认方案。
- 因为主代理已经自检通过而降低检查强度。

### 2.3 任务执行者

任务执行者一次只领取一份执行任务单。任务单是执行契约，执行者不依赖规划会话中的隐含信息。

必须负责：

- 读取当前工作区规则并核对任务声明的前置依赖是否真实达成。
- 重新验证任务单中的现状锚点；发现基线漂移时停止并反馈。
- 只在任务授权范围内修改和验证。
- 执行任务规定的验收，并区分已验证、未验证和无法验证。
- 将执行结果写入独立执行记录或返回给协调者，不修改稳定任务规格。

不得负责：

- 根据“可能可以并行”自行忽略前置依赖。
- 因顺手重构或补齐其他任务而扩大范围。
- 从任务描述推断 Git 提交、推送、合并、部署或外部数据变更授权。
- 将未运行的测试、静态阅读或子模块局部通过表述为整体完成。

## 3. 来源权限模型

规划和审核必须区分“规范性来源”与“事实性来源”。这是避免审核者重新设计方案的核心约束。

| 来源类型 | 作用 | 权限 |
|---|---|---|
| 用户明确确认的需求与决策 | 决定要实现什么 | 规范性来源 |
| 当前《实施方案与计划》 | 决定采用什么实施路径 | 方案确认前是待审对象；确认后成为唯一方案基线 |
| 当前代码、测试、配置、数据和项目规则 | 验证方案或任务是否符合现实 | 事实性来源，只能证明或推翻事实，不能自行产生新需求 |
| 历史方案和历史审核记录 | 解释演进过程、验证旧问题是否关闭 | 辅助来源，不得覆盖当前基线 |
| 聊天记忆、模型常识和审核者偏好 | 帮助发现检查方向 | 不具备方案决定权 |

开发工具包审核时，主流程必须显式提供：

1. 已确认方案的准确文件路径和基线标识。
2. 当前开发工具包路径。
3. 允许用于事实核验的代码工作区和项目规则路径。
4. 审核记录输出目录。
5. 明确禁止作为方案依据的历史文档或未确认草稿。

审核者可以因为代码事实与方案冲突而判定“不通过”，但不能自行选择替代方案。需要改变基线时必须返回主流程，由用户决定。

## 4. 完整生成时间线

```text
读取已确定需求和项目规则
          ↓
核验当前代码与工程事实
          ↓
生成或修订《实施方案与计划》
          ↓
实施规划者自检
          ↓
委托独立审核者审核方案并创建审核记录
          ↓
有阻断问题 ──→ 修订方案 ──→ 重新自检、重新审核
          ↓
无未解决阻断问题
          ↓
用户确认方案基线                     ← 唯一常规用户确认断点
          ↓
直接生成完整开发工具包
          ↓
实施规划者自检
          ↓
委托独立审核者审核开发工具包
          ↓
实施层问题 ──→ 修订工具包 ──→ 重新自检、重新审核
          ↓
无未解决阻断问题
          ↓
生成《目标与实施边界》
          ↓
执行最终一致性检查并结束规划流程
```

开发工具包审核发现以下情况时，不进入自动修订循环，而是重新请求用户确认：

- 必须改变已确认的功能目标、范围、非目标或总体实施路径。
- 必须增加具有独立产品含义的新能力。
- 必须改变用户已经明确决定的安全、兼容、迁移或交付原则。
- 方案与当前代码事实发生冲突，且存在多个有实质差异的处理方向。

## 5. 方案基线与防漂移

用户确认不能只存在于规划会话的隐含上下文中。确认后必须形成可被后续会话识别的基线：

- 给《实施方案与计划》设置明确版本和状态。
- 记录确认日期、确认范围和用户明确确认的依据。
- 开发工具包索引和独立审核记录引用方案的准确版本及内容摘要值。
- 方案确认后的任何实质修改都生成新版本；不得覆盖原基线后继续沿用旧确认。
- 只有拼写、格式和不改变含义的修正可以不重新确认，但必须保证摘要值同步更新并留下变更说明。

摘要值用于防止“审核通过后文件被修改”或“工具包引用了错误版本”，不能替代人类对方案内容的确认。

## 6. 审核记录协议

### 6.1 文件所有权

- 实施规划者只创建审核记录目录，不预创建初审或复审文件。
- 每次审核由独立审核者创建一个新文件。
- 审核记录只追加，不覆盖、不合并、不删除历史记录。
- 同一审核目录同一时间只允许一个审核者创建文件，避免顺序号冲突。

### 6.2 文件命名

默认采用人类可读的顺序号：

```text
YYYYMMDD-NN-方案初审.md
YYYYMMDD-NN-方案复审.md
YYYYMMDD-NN-开发工具包初审.md
YYYYMMDD-NN-开发工具包复审.md
```

审核者在写入前扫描目录，取当前最大顺序号加一。若未来允许同一对象被多个审核者同时审核，应改为包含时分秒或唯一后缀的命名方式，不能继续依赖单一顺序号。

### 6.3 最小内容

每份审核记录至少包含：

- 审核对象、版本、内容摘要值和审核时间。
- 实际读取的规范性来源与事实性来源。
- 未覆盖的检查范围及原因。
- 阻断问题、应修问题和改进建议。
- 对上一轮问题的关闭情况；复审时仍需检查新引入问题。
- 最终结论：通过或不通过。

“通过”表示没有未解决的阻断问题，不表示不存在任何建议。审核者不得把未验证范围默认为通过。

## 7. 开发工具包的最小结构

开发工具包不是任务拆分草案，而是一次生成的完整执行契约。目录是否分阶段由方案复杂度决定，不强制二级目录。

工具包索引至少记录：

- 对应的方案基线版本和内容摘要值。
- 工具包覆盖范围及明确不包含内容。
- 全部任务及其前置依赖。
- 需要执行者复核的共享工程规则和权限边界。
- 工具包级整体验收出口。

每份执行任务单至少记录：

- 任务名称和稳定编号，例如 `任务-01-<名称>`；编号只用于引用，不表示优先级。
- 对应方案章节和要实现的可观察结果。
- 开工前必须成立的事实性前置依赖及验证方法。
- 当前实现与必须在开工时重新核验的代码锚点。
- 允许修改的范围、明确禁止的范围和外部变更授权边界。
- 必须完成的实现要求。
- 可以判定通过或失败的验收步骤与证据。
- 发现基线漂移、依赖未满足或需要改变方案时的停止条件。
- 执行完成后必须返回的结果格式。

任务规格和执行记录必须分离。任务执行者不得把提交号、运行日志和临时结论持续追加到稳定任务单中。

## 8. 开发工具包自检

实施规划者生成工具包后，先完成以下自检，再委托独立审核：

1. 建立“方案要求到任务”的覆盖关系，确保每项实施要求至少落入一个任务，或明确说明不产生开发任务的原因。
2. 确认不存在未被任何任务承担的数据库、接口、前端、配置、迁移、兼容、发布或验收责任。
3. 检查所有前置依赖引用真实存在且没有循环依赖。
4. 检查任务边界是否形成可观察的完整结果，而不是按技术层机械切碎。
5. 检查两个任务是否因大量修改面重叠而形成隐含耦合；必要时合并任务或增加真实前置依赖。
6. 检查所有验收要求都有明确判定方式，并标识需要真实环境、数据或人工授权的部分。
7. 检查任务没有预设并行组；运行时仅根据依赖、工作区状态和冲突风险决定是否并行。
8. 检查任务没有继承规划会话中的隐含信息。

正式技能可以配套一个只负责结构检查的脚本，自动发现缺少必填字段、失效任务引用、重复编号、循环依赖和方案基线不一致。脚本不得声称能够替代语义审核。

## 9. 对抗性检查

以下检查从失败者或不可靠智能体的角度攻击当前设计，并给出对应约束。

| 攻击或失败场景 | 可能造成的结果 | 设计约束 |
|---|---|---|
| 需求仍未确定，规划技能为了完成任务强行补齐决策 | 伪确定方案进入开发 | 入口检查发现目标、范围或关键路径未决时停止，不生成工具包 |
| 规划者把自检文件命名为“独立审核” | 审核失去独立性 | 审核必须由另一个会话或子代理创建；无法启动独立上下文时不得宣称审核完成 |
| 审核提示泄露规划者的预期答案或自检结论 | 审核者只验证主代理观点 | 只传原始产物、来源清单和通用检查契约，不传预期结论或疑似问题答案 |
| 审核者从历史方案或个人偏好重新设计 | 已确认方案被静默替换 | 已确认方案是唯一规范性方案来源；替代方案只能作为需要用户决定的冲突报告 |
| 限定方案来源被误解为禁止查看代码 | 方案与现实矛盾无法发现 | 允许代码和项目规则作为事实性来源，但不得让事实性来源自动产生新需求 |
| 用户确认后方案文件被覆盖 | 工具包和审核针对不同版本 | 使用版本、状态和内容摘要值绑定方案、工具包与审核记录 |
| 工具包任务很多，看似完整但遗漏一项跨任务责任 | 开发结束后才发现缺口 | 工具包自检和独立审核都必须检查方案要求到任务的覆盖关系 |
| 为了便于分工按前后端或仓库机械拆分 | 每个任务都无法独立验收，执行会话互相等待 | 用可观察结果、稳定范围和独立验收判断粒度，必要时跨技术层形成一个任务 |
| 任务只写“前置任务完成”，不验证真实结果 | 错误完成声明向后传播 | 前置依赖必须描述应存在的事实或证据，执行者开工时重新核验 |
| 任务单使用精确行号但代码已经变化 | 执行者按过期锚点修改错误位置 | 锚点用于定位而非授权；开工第一步重新核验，不成立就停止 |
| 自动审核把任何建议都视为失败 | 修订循环永不结束 | 只有未解决阻断问题阻止推进，非阻断建议单独记录 |
| 规划者与审核者在同一问题上反复争执 | 无限循环消耗上下文 | 同一阻断问题连续两轮没有实质进展时停止，由用户处理方案解释或扩大事实核验 |
| 审核发现必须改变方案，规划者只改任务单绕过确认 | 用户确认失效 | 任何方案级变化都返回唯一用户确认断点，形成新基线后重新生成受影响工具包 |
| 多个审核者同时按 `NN` 创建记录 | 文件名碰撞或记录覆盖 | 默认审核串行；需要并发审核时改用时间戳或唯一后缀 |
| 《目标与实施边界》为了简洁省略重要限制或增加新承诺 | 人类读到的总结与执行契约不一致 | 最后从已确认方案和已审工具包派生，并做反向一致性检查；总结不得成为新的方案来源 |
| 执行者将提交、部署理解为任务的隐含步骤 | 发生未经授权的外部变更 | 每份任务单显式列出权限边界；未授权操作保持禁止 |
| 多个执行会话修改相同工作树 | 用户改动被覆盖或任务互相污染 | 产物只写依赖和修改范围；运行时协调者在启动前检查工作树、文件所有权和冲突风险 |
| 子代理不可用但主流程仍继续生成最终总结 | 自动审核被悄悄跳过 | 无法获得独立审核时停止在审核阶段，明确报告未完成条件 |

## 10. 当前建议的进入下一步条件

只有同时满足以下条件，实施规划流程才可以生成《目标与实施边界》并结束：

- 用户已经明确确认方案基线。
- 开发工具包引用的方案版本和内容摘要值与确认基线一致。
- 实施规划者自检完成。
- 独立审核记录由另一个会话或子代理生成。
- 独立审核结论为通过，且没有未解决阻断问题。
- 生成总结后的一致性检查没有发现总结、方案和工具包相互冲突。

## 11. 正式制作时的结构建议

每个正式技能保持独立目录，只放运行所需内容：

```text
plan-feature-implementation/
├── SKILL.md
├── agents/openai.yaml
├── references/
└── scripts/                 # 仅在确认需要结构校验后创建

review-feature-artifacts/
├── SKILL.md
├── agents/openai.yaml
└── references/

execute-feature-task/
├── SKILL.md
├── agents/openai.yaml
└── references/
```

研究背景、设计过程、测试记录和复盘材料继续放在当前 `skill-research/plan-feature-execution/`，不复制进正式技能，以免技能上下文膨胀。

## 12. 尚待真实样本验证

以下内容不需要现在再增加用户确认断点，但正式制作前应使用真实样本验证：

- 三个技能的触发描述是否会相互误触发。
- 一个大方案和一个中等方案是否都能适配同一任务粒度规则。
- 内容摘要值和方案版本的记录方式是否足够简洁。
- 独立审核提示是否能在不泄露主代理判断的情况下发现遗漏。
- 结构校验脚本需要哪些最少的机器可读字段。
- 任务执行技能在工作树脏、前置依赖失效和授权不足时能否正确停止。
